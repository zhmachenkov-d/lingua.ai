---

## 1. Контекст и цель

Заказчик хочет спроектировать ИИ-агента для самостоятельного изучения английского языка, который сочетает:

- работу с **учебником** (структурированный материал, грамматика, юниты);
- пополнение словарного запаса из **Oxford Dictionary** (определения, примеры, аудио, коллокации);
- **современные практики изучения языков** (SLA/ISLA: SRS, i+1, TBLT, микрообучение, focus on form, формативное оценивание, CEFR-выравнивание).

**Цель данного документа:** поставить ИИ-агенту задачу провести исследование и выдать на выходе **комплект проектной документации**, достаточный для принятия решения о разработке и для передачи в реализацию (MVP → Stage 2 → Stage 3).

**Ключевое требование к результату:** документ должен быть _применимым_ — не обзор, а готовые к использованию спецификации: архитектура, модели данных, промпты, сценарии, план внедрения.

---

## 2. Роль исполнителя

Ты — **исследователь + системный проектировщик + техлид**. Твоя задача — не писать код, а выдать:

- обоснованные **решения** (с альтернативами и trade-offs);
- готовые **артефакты** (схемы, спецификации, промпты, чек-листы);
- **приоритизированный план** внедрения.

Ты работаешь автономно, но каждое существенное решение фиксируешь с обоснованием и ссылкой на источник (исследование, документация API, практика).

---

## 3. Область работ (Scope)

### 3.1. Входит в scope

1. Исследование современных практик изучения языков и их перевода в требования к агенту.
2. Анализ конкурентов и существующих решений.
3. Техническое исследование: LLM, оркестрация, RAG, SRS, Oxford API, ASR/TTS.
4. Проектирование архитектуры (слои, агенты, память, инструменты).
5. Проектирование моделей данных (профиль, словарь, ошибки, прогресс).
6. Проектирование сценариев взаимодействия (user flows).
7. Дизайн промптов для ключевых агентов.
8. Скоупинг MVP и дорожная карта Stage 1–3.
9. Риски, ограничения, критерии успеха.

### 3.2. Не входит в scope

- Написание production-кода.
- UI/UX-дизайн (только логика экранов/сценариев).
- Юридическая экспертиза лицензий Oxford API (только флаги).
- Маркетинг и монетизация.

## 4. Deliverables (что должно быть на выходе)

Исполнитель обязан выдать **9 артефактов**. Каждый — отдельный раздел итогового документа (или отдельный файл). Для каждого артефакта указан **формат** и **критерии приёмки**.

### D1. Отчёт по современным практикам (Research: SLA/ISLA)

**Формат:** таблица «Практика → принцип → как реализуется в агенте → метрика проверки».
**Обязательный минимум практик:**

- Интервальное повторение (FSRS vs SM-2 — обосновать выбор).
- Comprehensible input / i+1 / 90% понимания.
- Task-Based Language Teaching (TBLT) — pre-task / main-task / post-task.
- Focus on Form в коммуникативном контексте.
- Обучение через ошибки + журнал ошибок + отложенная обратная связь.
- Микрообучение (microlearning) с генеративным ИИ.
- Формативное оценивание и интерпретируемая обратная связь.
- CEFR-выравнивание и mastery-based progression.
- Обучение на основе предложений, а не изолированных слов.
- Сбалансированное явное + имплицитное обучение.

**Критерии приёмки:**

- Каждая практика содержит ссылку на источник (исследование/обзор/документация).
- Для каждой указано, какой компонент архитектуры её реализует.
- Для каждой указана метрика, по которой можно проверить, что практика работает.

---

### D2. Конкурентный анализ

**Формат:** таблица «Продукт → сильные стороны → слабые стороны → что заимствуем / чего избегаем».
**Обязательный минимум:** Duolingo, Anki, LingQ, Busuu, Memrise, Quizlet, Elsa Speak, ChatGPT-репетиторы, специализированные SRS-приложения.
**Критерии приёмки:**

- Минимум 8 продуктов.
- Для каждого — вывод «применимо / не применимо к нашему агенту» с обоснованием.

---

### D3. Техническое исследование (Tech Research)

**Формат:** таблица «Компонент → варианты → критерии выбора → рекомендация → обоснование».
**Обязательные компоненты:**

- LLM (DeepSeek / GPT-4o / Claude / др.) — с учётом русского интерфейса и стоимости.
- Оркестрация агентов: LangGraph vs Dify vs Coze vs кастом.
- Векторная БД: Qdrant / Chroma / Pinecone / pgvector.
- SRS: FSRS (библиотеки) vs SM-2 (реализация).
- Oxford Dictionaries API: доступные endpoints, лимиты, лицензия, формат ответа.
- ASR/TTS: Whisper / Azure Speech / др. (опционально).
- Хранение профиля: реляционная БД vs документная.

**Критерии приёмки:**

- Для каждой рекомендации указан trade-off (что теряем).
- Для Oxford API — конкретный список полей, которые будем использовать (definition, examples, audio, synonyms, collocations, CEFR-метка если есть).
- Для SRS — обоснование FSRS с указанием, какая библиотека/реализация.

---

### D4. Архитектура системы

**Формат:** текстовая схема + описание слоёв + таблица агентов.
**Обязательные элементы:**

- 4 слоя: Восприятие → Когнитивный/Планирующий → Память → Действия/Инструменты.
- Таблица агентов: Router, Tutor, Vocabulary, Review, (+ Critic на Stage 3) — роль, вход, выход, инструменты, триггер.
- Схема взаимодействия агентов (кто кому передаёт управление).
- Явное разделение краткосрочной и долгосрочной памяти.

**Критерии приёмки:**

- Схема воспроизводима в виде диаграммы (Mermaid или текстовое описание).
- Для каждого агента указан его системный промпт-контракт (вход/выход/ограничения).
- Показано, как реализуется каждая практика из D1.

---

### D5. Модель данных

**Формат:** описание сущностей + поля + связи (ER-описание или JSON-схемы).
**Обязательные сущности:**

- `LearnerProfile` (CEFR по навыкам, цели, ограничения).
- `VocabularyItem` (слово, источник: учебник/Oxford, статус: Unseen→Learning→Review→Mastered, SRS-данные: stability, difficulty, next_review).
- `ErrorLog` (тип ошибки, контекст, частота, связанное правило/слово).
- `TextbookUnit` (юнит, текст, грамматика, список слов, статус прохождения).
- `Session` (краткосрочная память: что делали, какие слова/правила затронуты).
- `ReviewRecord` (результат повторения, качество ответа, timestamp).

**Критерии приёмки:**

- Для каждой сущности — поля с типами.
- Показано, как SRS-алгоритм использует поля `VocabularyItem`.
- Показано, как `ErrorLog` связан с `ReviewRecord` и `VocabularyItem`.

---

### D6. Сценарии взаимодействия (User Flows)

**Формат:** пошаговые сценарии (текст + Mermaid sequence diagram для ключевых).
**Обязательные сценарии:**

1. **Работа с учебником:** загрузка юнита → разбор → извлечение слов → добавление в SRS.
2. **Разбор слова из Oxford:** запрос → получение данных → объяснение → добавление в SRS.
3. **Ежедневное повторение:** Review Agent → выборка слов → генерация контекста → проверка → обновление SRS.
4. **Микрообучение (5 минут):** Router → выбор микро-задачи → выполнение → фидбэк.
5. **TBLT-сессия:** выбор задачи → pre-task → main-task → post-task → фиксация ошибок.
6. **Работа с ошибками:** журнал ошибок → паттерн → мини-упражнение → проверка.

**Критерии приёмки:**

- Каждый сценарий показывает, какие агенты задействованы и какие данные читаются/пишутся.
- Для каждого сценария указана практика из D1, которую он реализует.
- Для TBLT и повторения — sequence diagram.

---

### D7. Дизайн промптов

**Формат:** готовые системные промпты + шаблоны с переменными.
**Обязательные промпты:**

- `Router Agent` — классификация намерения + маршрутизация.
- `Tutor Agent` — объяснение материала учебника с RAG-контекстом.
- `Vocabulary Agent` — объяснение слова с опорой на Oxford API (запрет на «галлюцинации»).
- `Review Agent` — генерация проверочного задания + формативная обратная связь.
- `CEFR-ограничитель` — шаблон, который подмешивается в генеративные промпты (i+1).
- `Context Generator` — генерация мини-текста с целевыми словами.

**Критерии приёмки:**

- Каждый промпт содержит: роль, входные переменные, правила, формат вывода, ограничения (анти-галлюцинации, CEFR).
- Для Vocabulary Agent — явное правило «не выдумывать определения, использовать только данные Oxford API».
- Для Review Agent — правило формативной обратной связи (объяснение + связь с источником).
- Промпты протестированы на 2–3 примерах (few-shot) внутри документа.

---

### D8. План внедрения (Roadmap)

**Формат:** этапы MVP → Stage 2 → Stage 3 с задачами, критериями готовности и оценкой трудозатрат (в днях/неделях).
**Обязательные элементы:**

- **MVP:** что входит (Router + Tutor + Vocabulary + простой SRS + CEFR-шаблоны + карта ошибок-лог).
- **Stage 2:** персонализация (Review Agent, TBLT-режим, микрообучение, формативное оценивание).
- **Stage 3:** расширение (голос, аутентичные задачи, Critic-агент, экспорт в Anki).
- Для каждого этапа — **Definition of Done** и **метрики успеха**.
- Явно указано, что **не делать на MVP** (anti-scope).

**Критерии приёмки:**

- Каждый этап имеет измеримые критерии готовности.
- Указаны зависимости между задачами.
- Есть оценка трудозатрат (диапазон).

---

### D9. Риски и ограничения

**Формат:** таблица «Риск → вероятность → влияние → митигация».
**Обязательные риски:**

- Лимиты и стоимость Oxford API.
- Галлюцинации LLM в объяснениях слов/грамматики.
- Перегрузка пользователя (слишком много повторений / сложный input).
- Качество RAG по учебнику (плохая векторизация → нерелевантные ответы).
- Стоимость LLM при масштабировании.
- Отсутствие CEFR-меток в Oxford API → как компенсировать.
- Ошибки SRS-алгоритма (неправильная калибровка → потеря мотивации).

**Критерии приёмки:**

- Для каждого риска — конкретная митигация (не «быть осторожным», а действие).
- Указаны риски, которые могут заблокировать MVP.

## 6. Формат итогового документа

Единый документ со структурой:

```

1. D1. Современные практики
2. D2. Конкурентный анализ

5. D5. Модель данных
6. D6. Сценарии
7. D7. Промпты
8. D8. Roadmap
9. D9. Риски
10. Приложения (источники, схемы, JSON-примеры)
```

**Требования к стилю:**

- Русский язык, профессиональный тон.
- Каждое решение — с обоснованием и trade-off.
- Схемы — Mermaid или текст.
- Примеры — конкретные (JSON, фрагменты промптов, таблицы).
- Никаких «водяных» разделов: каждый абзац несёт решение или факт.

## 7. Критерии успеха всего проекта (Definition of Success)

Документ считается готовым, если:

1. По нему можно **начать разработку MVP** без дополнительных исследований.
2. Все 9 deliverables присутствуют и прошли критерии приёмки.
3. Каждая современная практика из D1 **прослеживается** до конкретного компонента в D4/D6/D7.
4. Roadmap содержит **измеримые** DoD и anti-scope.
5. Риски имеют **действенные** митигации.
6. Executive Summary позволяет заказчику **принять решение** за 5 минут чтения.

## 8. Ограничения и допущения

- Предполагается, что заказчик предоставит доступ к Oxford Dictionaries API (или подтвердит, что доступ будет получен до MVP).
- Учебник — один основной (конкретный), но архитектура должна допускать добавление других.
- Интерфейс MVP — текстовый чат (Telegram-бот или веб).
- Язык объяснений — русский, целевой язык — английский.
- Бюджет на LLM — умеренный (предпочтение моделям с хорошим соотношением цена/качество).
